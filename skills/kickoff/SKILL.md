# Kickoff — 착수 전 기획·디자인 검토

일을 시작하기 전에 "무엇을, 어떻게 만들지"를 사용자가 이해하고 고르게 하는 대화형 워크플로우다.
끝까지 자동으로 돌지 않는다. 사람이 답하는 지점(질문 카드)이 중심이고, 정한 것은 모두 문서에 남긴다.

두 방식으로 쓸 수 있다. 둘 다 같은 `brief.md`를 읽고 쓰므로 중간에 바꿔도 된다.
- **대화창(기본):** 질문 카드는 `AskUserQuestion`, 현황은 채팅 표로 보여준다.
- **화면:** 사용자가 "화면으로", "UI로", "화면 열어줘"라고 하면 로컬 웹 화면을 연다. 현황판, 작업별 문서 탭, 답할 카드, 받은 답 결정, 질문지 복사가 들어 있다. 절차는 [references/ui-mode.md](references/ui-mode.md).

## 원칙

- **근거 없는 지적은 쓰지 않는다.** 검토 항목마다 원문 위치를 단다: PRD 절·문장, Figma 노드 id, Jira 필드, Slack 스레드 링크(없으면 받은 파일:줄), 코드 `path:line`, 법령 조문·공식 문서 URL.
  - `모순`이면 두 원문 문장을 따옴표로 그대로 인용한다.
  - `누락`은 "입력 전체에 언급 없음(검토한 파일 목록)"을 근거로 인정한다.
  - 검토한 입력 파일 목록은 `sources.md` '검토한 입력' 절에 한 번만 적고, 누락 근거는 "입력 전체에 언급 없음(sources.md 검토한 입력)"으로 가리킨다.
  - 법·정책 같은 외부 근거는 웹 검색으로 확인한다. 법령 원문(국가법령정보센터 등)을 직접 봤으면 `확인`, 2차 자료만 찾았으면 `확인 필요`로 `sources.md`에 적는다. 출시 국가가 여럿이면 국가마다 확인한다.
- **원문이 이미 정한 것은 묻지 않는다.** 예를 들어 "웹으로 먼저", "디자인은 기존 토글 재사용"이라고 적혀 있으면 요구사항 출처로 쓰고 끝낸다. 그 결정과 어긋나는 선택지도 카드에 넣지 않는다. 제품을 "앱"처럼 일반 명칭으로 부른 것은 모순이 아니다.
  - 어긋남은 원문이 명시한 값을 뒤집는 경우만이다. 원문이 정하지 않은 값(시간 범위, 적용 대상 등)은 선택지로 물어도 된다.
  - "~할 듯", "나중에"는 방향과 시점을 정한 것으로 본다. 묻지 말고 다시 볼 조건(예: 광고는 주간 방문자 ○명 이후)을 범위표 비고에 추천으로 적는다.
  - Jira 하위 작업·티켓 이름(예: "BE-1201 일괄 다운로드 API")은 그 작업이 있다는 사실일 뿐, 방식이 정해졌다는 근거가 아니다.
- **모르는 값은 지어내지 않는다.** 추천 기본값을 붙여 질문으로 남기고 상태를 `추천(확인 전)`으로 둔다. 결정 주체가 답해야 `정함`이 된다.
- **사용자가 이해하고 고른다.** 설계 선택지는 쉬운 말로 무엇이 달라지는지, 비용, 나중에 바꾸기 쉬운지를 적고, 추천 하나를 이유와 함께 고른다.
- **질문지는 초안까지만 만든다.** Slack·Jira로 보내는 일은 사용자가 요청할 때만 한다. 보내기 전에 받는 사람과 본문을 보여주고 확인받는다.
- **문서에 적어야 정한 것이다.** 대화에서 정한 것도 `brief.md`에 옮긴다.

## 산출물

작업 폴더: `~/kickoff/<YYMMDD>-<slug>/` (사용자가 다른 곳을 말하면 그곳). slug는 영문 소문자·숫자·`-`로 쓴다. 0장 작업 id는 Jira 키가 있으면 키, 없으면 폴더 이름과 같게 쓴다.

| 파일 | 내용 |
|---|---|
| `sources.md` | 수집한 입력의 식별값(티켓 키, 페이지 id·version, Figma 파일·노드 id, 수집 시각), 원문 발췌, '검토한 입력' 목록. 대상 저장소가 있으면 읽은 파일의 `path:line` 발췌와 기준 SHA, 새 프로젝트면 '참고 코드' 절에 사용자의 기존 저장소 스택을 적는다 |
| `brief.md` | 정리 문서. [assets/brief-template.md](assets/brief-template.md)를 복사해 채운다. 절을 빼거나 순서를 바꾸지 않는다 |
| `questions.md` | 회사 작업의 담당자별 질문지. [assets/questions-template.md](assets/questions-template.md) 형식. 개인 작업이면 만들지 않는다 |
| `cards.json` · `inbox.json` | 화면 모드에서만. 에이전트가 낸 카드와 사용자가 화면에서 남긴 답. 형식은 [references/ui-mode.md](references/ui-mode.md) |

## 작업 순서

### 1. 입력 받기

- 받을 수 있는 것: Jira 키·링크, Confluence URL, Figma URL(노드 포함), Slack 스레드 링크, 로컬 문서, 텍스트 메모, 대상 저장소 경로.
- 회사/개인은 전역 CLAUDE.md '적용 범위'로 판단한다. 개인 작업이면 Atlassian 도구를 쓰지 않는다.
- 회사 작업이면 Jira 키와 담당자(기획·디자인·백엔드) 이름을 찾는다. 기획·백엔드는 Jira 보고자·하위 작업·PRD 작성자에서, 디자인은 Figma 파일 소유자·마지막 수정자와 Jira 댓글에서 찾는다. 못 찾으면 질문지 묶음 제목을 "<역할> — 담당자 미확인"으로 두고 보고의 '직접 하실 일'에 적는다.
- 요청자가 직접 물은 것(예: "이번 스프린트 안에 가능할까요?")은 0장 '요청자 질문'에 적고, 언제 어떻게 답할지를 보고에 넣는다.
  - Jira 키를 모르면 0장 작업 id에 `YYMMDD-slug (Jira 키 없음)`을 쓰고, 5장에 `누락`·`중요` 항목으로 올린 뒤 진행한다. 이 스킬은 코드를 고치지 않으므로 키 없이 검토해도 된다. 다음 단계(`jira-bhsn`)로 넘기기 전에만 확정한다.
- 개인 새 프로젝트면 `~/Desktop/pro/` 아래에 관련 폴더가 있는지 확인한다. 이미 쓰는 저장소(예: `breeder_web`)의 스택을 `sources.md` '참고 코드'에 적는다. 이름이 비슷해도 내용이 무관하면 "무관"으로 적고 설계 대안으로 내지 않는다.
- 빠진 입력은 따로 묻지 말고 5단계 첫 카드 호출에 합친다. 디자인 유무는 단독 문항(있음 — 링크 / 없음 — 기존 컴포넌트로)으로 묻고, 새 프로젝트의 저장소는 6단계 설계 카드로 묻는다. 끝까지 없으면 없는 대로 진행하고 검토 항목으로 남긴다.

### 2. 수집하고 고정한다

| 출처 | 방법 |
|---|---|
| Jira | `jira_get_issue` — 설명, 하위 작업, 링크된 이슈, 댓글 |
| Confluence | `confluence_get_page` — 본문과 version 번호. 하위 페이지·첨부는 필요한 것만 |
| Figma | `get_metadata`로 프레임 목록과 이름, `get_screenshot`으로 화면. 문구·컴포넌트가 필요하면 `figma:figma-design-to-code` 스킬을 먼저 읽고 `get_design_context` |
| Slack | `slack_read_thread` |
| 코드 | 위치를 아는 파일 1~2개는 직접 읽는다. 위치를 모르고 3개 이상 훑어야 하면 `Agent(subagent_type: "Explore", model: "haiku")`에 맡겨 경로·라인만 받는다. 판단이 필요하면 `model: "sonnet"` |

- 도구가 연결되지 않으면 사용자에게 알리고 붙여넣기로 받는다.
- 식별값과 발췌를 `sources.md`에 적는다. 이후 모든 근거는 이 파일이나 원문 위치를 가리킨다.

### 3. 내 말로 다시 쓴다

`brief.md` 1~4장을 채운다.
- 요구사항은 `R-n`으로 "누가 / 무엇을 / 완료 조건 / 출처"를 한 행에 쓴다.
- 원문에 없는데 추론한 요구사항은 출처를 `추론` 또는 `추론 — <path:line>`으로 적고, 같은 내용을 5장 검토 항목에도 올린다.
- 범위표는 항목마다 `이번`/`범위 밖`과 확인 방법(`자동 검사`/`사람 확인`)을 적는다.

### 4. 체크리스트로 검토한다

- [references/checklist.md](references/checklist.md)의 관점(기획·디자인·개발·QA, 새 프로젝트면 '새 프로젝트')을 하나씩 확인한다. 해당 없는 항목은 적지 않는다.
  - 디자인 파일이 없으면 D2(상태)·D3(문구)·D7(다국어 길이)·D9(기존 컴포넌트)만 원문과 기존 코드 기준으로 본다.
  - E5(오래 걸리는 처리)에 해당하면 진행 표시·취소·재시도와, 새로고침·화면 이탈 뒤 진행 중 작업을 다시 찾는 방법을 D2 화면 상태와 함께 확인한다. 추천안에 취소가 없으면 "취소 없음 — 이유"를 적는다.
- 원문(Jira·PRD·Figma 요약·Slack, 코드 제외) 합계가 3,000자(`wc -m`) 이상이거나 입력에 있는 화면이 5개 이상이면 관점별 서브에이전트를 한 메시지에서 병렬로 띄운다.
  - `Agent(model: "sonnet")`에 `sources.md`·`brief.md` 경로, 맡은 관점의 체크리스트 절, 근거 규칙을 넘기고 항목 목록만 받는다.
  - 메인은 결과를 합치면서 중복을 묶고, 원문에서 근거를 확인할 수 없는 항목은 버린다.
- 항목은 `brief.md` 5장에 `Q-n`으로 적는다.

| 필드 | 값 |
|---|---|
| 체크 | 해당 체크리스트 번호(예: `P7`, `E5`). 체크리스트 밖의 입력 문제(Jira 키 없음 등)는 `입력` |
| 유형 | `누락` · `모순` · `모호` · `위험` |
| 근거 | 원문 위치 |
| 영향 | `막힘`(답에 따라 설계·일정, 또는 API 필드·저장 데이터가 갈라진다. 선택지 하나라도 API 필드·저장 데이터를 늘리면 추천이 그걸 피해도 막힘) · `중요`(틀리면 다시 만든다) · `사소`(관례대로 해도 된다) |
| 결정 주체 | `기획` · `디자인` · `백엔드` · `법무` · `본인`(이 스킬을 쓰는 사용자). 이름은 `디자인(김OO)`처럼 괄호로 붙인다(현황판은 괄호 앞 역할로 묶는다). 둘이면 `기획+디자인` |
| 추천 | 기본값과 이유 한 줄 |
| 상태 | `열림` → `추천(확인 전)` / `질문함` → `답 옴` → `정함`, 또는 `범위 밖` |
| 답 | `정함`: 답 요지와 출처 / `질문함`: `질문함 — <담당자>, <YYYY-MM-DD>[, <채널 링크>]` / `답 옴`: 받은 답 요지와 출처 / `추천(확인 전)`: 비움 |

- 추천 기본값이 근거로 든 법·정책·기존 동의 구조와 충돌하지 않는지 확인한다. 법·규제가 걸리면 추천 이유로만 쓰지 말고 `위험` 항목으로 따로 올린다. 추천을 따르면 피할 수 있으면 `중요`, 피할 수 없으면 `막힘`으로 둔다. 해석이 갈리면 결정 주체는 `기획+법무`로 둔다.
- 회사 작업에서 목표·성공 지표·정책(P1·P8·P10·P12)은 결정 주체가 `기획`이고 영향은 `중요` 이상이다. 본인이 "없이 진행"으로 닫지 않고, '기본값으로 진행할 항목'에도 넣지 않는다.

### 5. 질문 카드로 답을 받는다

1. 채팅에 먼저 짧게 보여준다. 6단계 설계 카드를 먼저 물어야 하면 그 설계 설명도 여기에 넣고, 첫 호출을 설계 카드로 한다.
   - 이해한 내용을 5줄 이내로 쓴다.
   - 검토 결과 수(막힘·중요·사소)와 결정 주체가 다른 사람인 항목 수를 쓴다.
   - 기본값으로 묶을 항목은 표로 보여준다.
2. `AskUserQuestion`으로 묻는다. 5·6단계 카드는 합쳐 호출 3번, 10문항 이내로 한다.
   - **형식:** 한 번에 4문항까지, 문항마다 선택지 2~4개, header는 12자 이내로 한다. 추천을 첫 번째에 두고 라벨 끝에 `(추천)`을 붙인다. description에는 고르면 무엇이 달라지는지 한 줄을 쓴다. 쓸 preview가 없으면 preview 키를 넣지 않는다. description에 brief 2~4장에 없는 기능을 꺼내지 않는다.
   - **단독 문항으로 묻는 것:** 본인 결정 중 `막힘`·`위험`, 핵심 값의 신뢰를 정하는 규칙(예: 제보 유효 시간, 허위 제보 처리), 체크리스트가 묶지 말라고 한 항목(N9 등), 디자인 유무.
   - **묶음 문항으로 묻는 것:** question에는 항목을 나열하지 말고 "n개(위 표)"로 쓰고, preview에 항목별 추천을 적는다.
     - 본인 기본값(`사소`, 그리고 6단계 설계 중 "나중에 바꾸기: 쉬움"인 것)이 2개 이상이면 "기본값 n개를 추천대로 확정 / 하나씩 보기"로 묻는다. 1개면 단독 문항으로 묻는다.
     - 다른 사람이 정할 `막힘`·`중요` 항목은 담당자마다 3개 이상이면 "<담당자> 항목 n개 모두 담당자에게 묻기 (추천) / 하나씩 보기"로 묻는다. 2개 이하면 단독 문항으로 묻고 선택지에 `담당자에게 묻기`를 넣는다.
     - 다른 사람의 `사소` 항목은 카드로 묻지 않는다. `questions.md`의 해당 담당자 묶음 끝 '기본값으로 진행할 항목'에 넣는다.
     - 10문항을 넘으면 본인 `중요` 항목도 "모두 추천대로 / 하나씩 보기" 묶음으로 돌린다. 단독 문항으로 묻는 것은 묶지 않는다.
   - **조합 선택지를 만들지 않는다.** 같은 결정의 세부값만 한 선택지로 묶는다(예: 혼잡도 3단계와 그 표시 문구). 서로 독립인 결정을 선택지 하나에 붙이면 조합을 고를 수 없다. 나쁜 예: "수험생 / 4주 주간 제보 100건".
3. 답에 따라 문서를 고친다.
   - 본인 항목에서 고른 것은 `정함`으로 바꾸고 답 칸에 `사용자 선택: …`을 쓴다. 고른 설계가 다른 담당자 범위에 걸치면(6단계 `제안`) 그 담당자의 동의를 묻는 Q를 `막힘`·`질문함`으로 따로 두고 D-n과 잇는다.
   - 다른 사람 항목에서 `담당자에게 묻기`를 고르면 `질문함`으로 바꾼다.
   - 다른 사람 항목에서 사용자가 값을 고르면(추천이든 다른 값이든) 추천 칸을 그 값으로 고치고 `추천(확인 전)`으로 둔다. 질문지에 "이 값으로 진행하려 합니다. 괜찮을까요?" 문항을 넣는다. 사용자가 "내가 정해도 된다"고 하면 `정함`으로 바꾼다.
   - 답으로 생긴 요구사항·범위·화면 상태는 2·3·4장에 반영한다. 출처는 `추론 → Q-n 정함`으로 쓴다.
4. 카드를 쓸 수 없는 환경이면 같은 내용을 번호 목록으로 채팅에 쓰고 답을 기다린다.
5. 화면 모드면 `AskUserQuestion` 대신 같은 규칙으로 `cards.json`을 쓰고 화면에서 답을 받는다([references/ui-mode.md](references/ui-mode.md)). 화면에서는 문항이 많아도 읽기 쉬우므로 한도를 20문항으로 늘린다.

개인 작업은 담당자가 사용자 자신이므로 모든 결정을 카드나 묶음 문항으로 묻는다. 묶음 선택지는 "모두 추천대로 / 하나씩 보기" 두 개다.

### 6. 설계를 고른다

- 6단계는 코드 구조를 정하는 선택만 다룬다: 라이브러리, 저장소·DB, 데이터 흐름, API 계약, 상태 관리, 공통 컴포넌트, 동기/비동기 처리, 캐시. 제품 규칙(누가 무엇을 할 수 있는지, 유효 시간 등)은 결정 주체가 본인이어도 5단계 카드로 묻는다.
- 본인 설계가 다른 담당자 질문의 전제가 되면 그 설계 카드를 5단계 담당자 항목보다 먼저 묻는다. 예: zip 생성 위치를 정해야 백엔드 API를 물을 수 있다.
- 선택지마다 한 줄 설명, 장점, 단점·비용, 나중에 바꾸기(쉬움/어려움), 기존 코드와의 관계(코드 근거)를 적는다. 대상 저장소가 없으면 `sources.md` '참고 코드'를 근거로 쓴다.
- 채팅에서 짧게 설명한 뒤 `AskUserQuestion`으로 고르게 한다. 전체 비교표(장점·단점·바꾸기·기존 코드)는 추천 선택지 `preview` 하나에 모든 안을 담고, 다른 선택지 description에는 핵심 단점 한 줄만 쓴다. 함께 쓰는 하나의 구조(예: DB와 갱신 방식)는 한 결정으로 묻는다.
- 원문의 하위 작업 이름 때문에 대안을 카드에서 빼면 D-n '버린 대안'에 이유를 적고 채팅 설명에 한 줄로 밝힌다.
- 실데이터·코드로도 갈리지 않고 공통 계약을 바꾸는 큰 결정이면(전역 CLAUDE.md §8) 그 판단만 `Agent(model: "fable")`에 묻는다. 확인한 사실과 선택지를 함께 넘긴다.
- 결정은 6장에 `D-n`으로 적는다(결정, 이유, 버린 대안, 관련 Q, 상태).
  - 다른 담당자 범위에 걸치는 결정은 상태를 `제안`으로 둔다. 질문지에는 "정했습니다"가 아니라 "FE는 ○○를 제안합니다"로 쓴다.
  - 담당자가 동의하면 `확정`으로 바꾼다.

### 7. 질문지와 정리 문서를 마무리한다

- `questions.md`(회사 작업):
  - 결정 주체별로 묶는다. 둘이 함께 정할 항목은 첫 주체 묶음에 두고, 다른 묶음에는 "[Q-n] ○○ 묶음과 같은 내용입니다"라고 한 줄만 쓴다. 다른 주체에게 사실 확인만 필요하면 그 묶음에 "[Q-n 관련] 확인 부탁" 문항을 따로 둔다.
  - 문항마다 맥락 한 줄, 질문, 선택지, "답이 없으면 ○○로 진행하겠습니다"를 쓴다. 선택지는 카드에서 보여준 것과 같게 쓴다. 다른 담당자의 답에 따라 달라지는 내용(예: 권한별 에러 코드)은 "Q-n 답에 따라 달라짐"이라고 표시한다.
  - 기한은 묶음 머리말에 적는다. 원문 일정(스프린트 종료일 등)이 있으면 그보다 2영업일 앞, 없으면 작성일 + 2영업일로 하고, 보고에 "임시 기한"이라고 밝힌다.
  - 기획·디자인 묶음의 맥락에는 코드 경로 대신 현재 서비스 동작을 쓴다(예: "현재 조회자는 원본을 받을 수 없음"). `path:line`은 `brief.md`에만 둔다.
  - Jira 키 확인이 필요하면 해당 담당자 묶음의 첫 문항으로 둔다.
  - 질문지에 넣은 Q의 답 칸은 `질문함 — <담당자>, <질문지 만든 날>`로 쓴다. 사용자가 "보냈어"라고 하거나 발송을 맡기면 보낸 날짜와 채널 링크(`slack:<스레드 링크>`, `jira:<키>`)로 고친다. 현황판은 이 날짜로 며칠째 기다리는지 센다.
  - 존댓말 업무 톤으로 쓴다. 담당자당 7문항이 넘으면 묶거나, `사소`는 '기본값으로 진행할 항목'으로 돌린다.
- `brief.md` 7장(구현 개요)과 8장(수용 기준)을 채운다. 수용 기준은 예/아니오로 판정할 수 있는 문장으로 쓴다.
- 0장 `상태`에 `검토 중`을 적고 `python3 <이 스킬 경로>/scripts/check_brief.py <brief.md>`를 실행한다.
  - 형식 오류는 고친다.
  - 출력된 판정으로 0장 `상태`를 바꾸고, 한 번 더 실행해 경고가 없는지 확인한다. `질문 대기`면 `질문 대기 (막힘 Q-a, Q-b)`처럼 미해결 막힘 Q를 괄호로 적고, 판정이 바뀔 때마다 괄호도 새로 쓴다.
  - 판정은 `막힘`만 센다. `중요` 항목이 `질문함`이면 보고에 따로 적는다.

### 8. 보고

- 착수 판정(`착수 가능` / `질문 대기` + 막힘 Q 목록)과 답을 기다리는 `중요` 항목. 질문 대기여도 먼저 시작할 수 있는 작업이 있으면 판정 옆에 적는다
- 요청자 질문(0장)에 언제 어떻게 답할지
- 정한 것 요약(D-n과 그 상태, 확정한 기본값 수)
- 회사 작업: 담당자별 질문 수와 `questions.md` 경로. 개인 작업: "담당자 질문 없음" 한 줄
- 다음 할 일. 막힘과 무관해서 먼저 시작할 수 있는 부분이 있으면 적는다
- 사용자가 직접 확인해야 할 일(법적 신고 대상, 약관, 테스트 계정 준비, 담당자 미확인 등)은 따로 적는다. 전역 CLAUDE.md §11에 따라 개인 할 일 목록에 추가하고 동기화한 뒤, 추가한 줄을 보고에 적는다

질문 발송을 요청받으면 회사 Slack은 `slack_send_message_draft`(초안)로, Jira는 `jira_add_comment`로 한다. 보내기 전에 받는 사람·채널·본문을 보여주고 확인받는다.

## 답 확인과 결정

담당자 답은 자동으로 `정함`이 되지 않는다. 먼저 `답 옴`으로 표시하고, 반영할지는 사용자가 정한다.

1. **답 모으기.** 다음 중 하나로 답을 받는다.
   - 사용자가 답을 붙여넣거나 Slack 스레드·Jira 링크를 준다.
   - 사용자가 "답 왔나 확인해줘"라고 하면, `질문함` Q의 답 칸에 적힌 채널(`slack:`·`jira:`)을 질문한 날짜 이후로 읽는다(`slack_read_thread`, `jira_get_issue` 댓글). 개인 작업이면 이 단계를 건너뛴다.
2. **표시.** 답이 온 Q를 `답 옴`으로 바꾸고, 답 칸에 답 요지와 출처(누가, 어디서, 날짜)를 적는다. 답이 어느 Q에 대한 것인지 애매하면 표시하지 않고 사용자에게 묻는다.
   - 한 답이 다른 Q에도 해당하는 내용을 담고 있으면 그 Q는 바로 바꾸지 않고, 3번 카드에서 "<Q-m>도 답 옴으로 볼까요?"를 함께 묻는다.
   - 답이 0장 '요청자 질문'에 답할 근거가 되면 보고에 요청자에게 보낼 답 초안을 적는다.
3. **사용자 결정.** Q마다 셋 중 하나를 고르게 한다. 대화창은 `AskUserQuestion`(답 요지를 description에), 화면은 '답할 것' 패널이다.
   - `반영`(추천): `정함`으로 바꾼다. 답 칸은 `<받은 답 요지와 출처> — 사용자 결정: 반영(<대화창|화면>, YYYY-MM-DD)`으로 쓴다. 동의받은 `제안` D-n은 `확정`으로 바꾼다.
   - `추가 질문`: Q는 `질문함`으로 되돌리고 오늘 날짜를 적는다. 추가 질문을 `questions.md`의 해당 묶음에 넣는다. 질문 내용이 새 주제면 Q를 새로 만든다.
   - `빼기`: `범위 밖`으로 바꾸고 답 칸에 이유를 적는다.
4. **반영.** 답으로 바뀐 내용을 1~8장 어디에 있든 고친다. 그 Q-n·D-n을 언급한 칸(2장 출처, 3장 비고, 6장 상태, 7장 순서·먼저 시작할 것, 8장 조건)을 `grep -n 'Q-n'`으로 찾아 "답 뒤 확정"·"제안" 같은 문구를 정한 값으로 바꾸고, 9장 변경 기록에 한 줄 남긴다.
5. **무응답.** 기한이 지나 기본값으로 진행하기로 하면 해당 Q를 `정함`으로 바꾸고, 답 칸에 `무응답 — 기본값 적용(날짜)`을 적는다.
6. `check_brief.py`를 다시 돌린다. 0장 상태가 `검토 중`·`질문 대기`·`착수 가능`이면 판정으로 바꾸고 보고한다.

## 작업 단계와 현황판

`brief.md` 0장 `상태`가 작업 단계다.
- `검토 중`·`질문 대기`·`착수 가능`은 `check_brief.py` 판정으로 정한다.
- `진행 중`·`보류`·`취소`·`완료`는 사용자가 정한다. 대화창에서 "이거 시작하자", "보류해", "안 하기로 했어"라고 하면 0장 상태를 바꾸고 9장에 이유를 한 줄 남긴다. 화면에서는 작업 화면의 단계 버튼으로 바로 바뀐다.
- 현황판은 이 단계로 열을 나눈다. 사용자가 지금 할 일이 있으면(아직 결정하지 않은 `답 옴` Q, 화면에서 답하지 않은 카드) 단계와 상관없이 '결정 필요' 열에 올린다. 제출만 하고 반영 전인 작업은 원래 열에 두고 '반영 대기'로 표시한다.

사용자가 "킥오프 현황", "작업 현황 보여줘"라고 하면 다음을 한다.
1. 화면에서 제출만 하고 아직 반영하지 않은 답(`inbox.json`의 `submitted: true`)이 있으면 먼저 반영한다([references/ui-mode.md](references/ui-mode.md)). `submitted: false`인데 답이 들어 있으면 반영하지 않고, 보고에 "화면에서 고르다 만 답 n개 — 제출하면 반영"을 한 줄 적는다.
2. `python3 <이 스킬 경로>/scripts/board.py`를 실행한다(`--all`이면 완료·취소 포함). 대화창이면 출력된 표를 그대로 보여주고, 화면이면 서버를 열어 주소를 알려준다.
3. '결정 필요' 작업이 있으면 "답 확인과 결정"으로 이어갈지 묻는다.

## 다음 단계로 넘기기

이 스킬은 코드를 고치지 않는다. 착수 가능이 되면 사용자가 원하는 다음 단계로 넘긴다.
- 큰 구현: `brief.md`를 입력으로 `hjjm-prd`로 PRD를 쓴다.
- 회사 작업: `jira-bhsn`으로 브랜치·PR을 진행한다.
- 테스트 케이스: `qa-testcase-gen`.
