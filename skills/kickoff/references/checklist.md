# 착수 전 검토 체크리스트

관점별로 확인한다. 각 항목은 "예/아니오"로 답하고, "아니오"이거나 원문이 서로 다르면 `brief.md` 5장 검토 항목(Q-n)이 된다.
해당 없는 항목은 건너뛴다. 근거(원문 위치)를 댈 수 없는 항목은 적지 않는다. `누락`은 "입력 전체에 언급 없음(검토한 파일 목록)"을 근거로 쓴다.
원문이 이미 정한 것은 검토 항목으로 올리지 않는다.

## 목차
1. 기획
2. 디자인
3. 개발
4. QA
5. 새 프로젝트 (처음 만드는 제품일 때만)

## 1. 기획

| # | 확인할 것 | 자주 빠지는 예 |
|---|---|---|
| P1 | 왜 하는지(문제)와 끝났다고 볼 기준(성공 지표)이 있는가 | "편하게", "개선"만 있고 수치나 판정 기준이 없음 |
| P2 | 누가 쓰는지와 역할별 권한이 정해졌는가 | 관리자·일반·조회 전용 사용자가 같은 화면을 볼 때 무엇이 다른지 없음 |
| P3 | 이번 범위와 범위 밖(비목표)이 나뉘었는가 | "추후"라는 말만 있고 이번에 할지 말지 없음 |
| P4 | 우선순위(필수/있으면 좋음)가 있는가 | 모두 필수로 적혀 있어 일정이 넘칠 때 뺄 것을 모름 |
| P5 | 기존 기능과의 관계(대체/변경/공존)가 적혀 있는가 | 새 화면이 생기는데 기존 화면을 없애는지 둘 다 두는지 없음 |
| P6 | 예외 흐름이 있는가: 실패, 취소, 중복, 한도 초과, 데이터 없음 | 정상 흐름만 있음 |
| P7 | 수치와 한도가 정해졌는가: 최대 개수, 글자 수, 파일 크기, 기간, 정렬 기준 | "여러 개", "대용량" 같은 표현 |
| P8 | 정책이 정해졌는가: 데이터 보관·삭제, 개인정보, 알림 시점, 과금 | 삭제하면 연결된 데이터는 어떻게 되는지 없음 |
| P9 | 출시 조건이 있는가: 기능 플래그, 단계적 공개, 공지, 이전 데이터 처리 | 기존 사용자에게 언제 어떻게 보이는지 없음 |
| P10 | 측정할 이벤트가 있는가 | 성공 지표는 있는데 측정할 방법이 없음 |
| P11 | 용어가 한 가지로 쓰이는가 | 같은 것을 "회원"·"사용자"로 섞어 씀 |
| P12 | 법·규제·플랫폼 정책을 지키는가: 광고성 정보 수신 동의(오후 9시~다음 날 오전 8시 전송은 별도 사전 동의 — 정보통신망법 제50조 제3항, 전자우편 등 시행령 예외 매체 제외), 개인정보·위치정보 수집 동의, 앱스토어 심사 정책 | 마케팅 알림에 새 규칙을 적용하면서 동의 없이 기본값을 켜짐으로 둠 |

## 2. 디자인

| # | 확인할 것 | 자주 빠지는 예 |
|---|---|---|
| D1 | 기획의 화면·요소가 디자인에 다 있는가, 디자인에만 있는 요소는 없는가 | 기획에 없는 버튼이 디자인에 있음 |
| D2 | 화면마다 상태가 그려졌는가: 기본, 로딩, 빈, 오류, 권한 없음. 오래 걸리는 작업이면 진행 중·취소·완료·일부 실패 | 빈 목록·오류 화면이 없음, 처리 중 취소 방법이 없음 |
| D3 | 문구가 기획과 같은가. 설정·토글처럼 효과가 눈에 안 보이는 항목에 적용 시간·대상을 알려 주는 보조 설명이 있는가 | 버튼 이름이 기획 용어와 다름, 토글만 있고 언제 적용되는지 설명 없음 |
| D4 | 긴 텍스트, 큰 숫자, 많은 항목에서 어떻게 보이는가 | 이름 말줄임 규칙 없음, 숫자 자릿수 표시 없음 |
| D5 | 화면 크기별(모바일·태블릿·데스크톱) 배치가 있는가 | 데스크톱만 있음 |
| D6 | 상호작용이 정해졌는가: 모달·시트·토스트·확인 대화상자, 진입·종료 방법, 뒤로 가기 | 삭제 확인을 묻는지 없음 |
| D7 | 다국어 문구 길이를 고려했는가(다국어 제품일 때) | 영어·일본어가 길어 버튼이 넘침 |
| D8 | 접근성: 대비, 포커스 순서, 터치 영역, 대체 텍스트 | 회색 글자 대비 부족 |
| D9 | 기존 디자인 시스템 컴포넌트를 쓰는가, 새 컴포넌트가 필요한가 | 기존 토글과 다른 새 토글 |

## 3. 개발

| # | 확인할 것 | 자주 빠지는 예 |
|---|---|---|
| E1 | 필요한 데이터와 출처가 정해졌는가: 어느 API·테이블에서 오는지 | 화면에 보이는 값의 출처가 없음 |
| E2 | API 계약이 정해졌는가: 요청·응답 필드, 페이징, 정렬, 에러 코드 | 백엔드와 합의 전인데 일정이 같이 잡힘 |
| E3 | 권한 확인을 어디서 하는가(서버/클라이언트) | 화면에서만 숨기고 서버 확인 없음 |
| E4 | 동시성·중복 처리: 두 번 누름, 여러 탭, 다른 사용자가 동시에 수정 | 중복 제출 방지 없음 |
| E5 | 처리 방식: 동기/비동기, 오래 걸리는 작업의 진행 표시·취소·재시도 | 대용량 처리인데 즉시 응답을 가정 |
| E6 | 성능 한도: 목록 크기, 응답 시간, 파일 크기 | 수천 건 목록을 한 번에 그림 |
| E7 | 캐시와 갱신: 무엇을 언제 다시 불러오는지 | 수정 후 목록이 갱신되지 않음 |
| E8 | 하위 호환과 이전: 기존 데이터·API·저장값에 미치는 영향 | 필드 이름이 바뀌어 기존 앱 버전이 깨짐 |
| E9 | 영향 범위: 바꾸는 공통 코드와 그걸 쓰는 다른 화면(코드 근거) | 공통 컴포넌트 수정이 다른 화면에 퍼짐 |
| E10 | 다국어 키, 설정값, 환경변수, 기능 플래그가 필요한가 | 새 문구·보조 설명 문구의 번역 키 일정 없음 |
| E11 | 실패를 알아챌 방법: 로그, 에러 모니터링, 알림 | 백그라운드 작업 실패가 조용히 묻힘 |
| E12 | 보안: 입력 검증, 파일 업로드 검사, 민감 정보 노출 | 공유 링크가 추측 가능 |
| E13 | 시각·시간대 기준: 서버가 시각으로 판정하면 사용자 시간대를 어디서 아는가(고정 / 기기 시간대 저장), 출시 국가 | 예약·마감 판정을 서버 시간(UTC)으로 함. "기기 시간대 저장"이 선택지에 있으면 API 필드가 갈리므로 `막힘`, 결정 주체 `백엔드` |

## 5. 새 프로젝트

처음 만드는 제품일 때만 본다. 대부분 결정 주체가 `본인`이므로 카드(제품 규칙은 5단계, 코드 구조는 6단계)로 묻는다.
기획·개발 항목과 겹치면(P1·P2와 N1·N2, E7과 N11 등) N 번호 하나로 적는다.

| # | 확인할 것 | 고를 때 볼 것 |
|---|---|---|
| N1 | 대상 사용자와 해결하는 문제 한 문장, 비슷한 서비스와 다른 점 | 한 문장으로 안 써지면 범위가 넓은 것 |
| N2 | 성공 지표 1개와 기한, 중단 기준 | 예: 4주 안에 주간 사용자 50명, 못 넘으면 접는다 |
| N3 | 수익 방식(없음/광고/구독/수수료)과 시점 | 수익화를 미루면 미룬다고 적고, 다시 볼 지표 조건을 함께 적는다 |
| N4 | 플랫폼: 웹, 앱(Android/iOS), 둘 다 | 입력에 이미 적혀 있으면 묻지 않는다. 앱이면 스토어 심사 조건(계정 삭제, 개인정보 처리방침)까지 범위에 넣는다 |
| N5 | 로그인 방식과 계정 삭제 | 비로그인으로 시작할 수 있는가 |
| N6 | 데이터 저장과 권한: DB, 행 단위 권한, 파일 저장소, 백업 | 기기 저장만으로 되는지, 사용자끼리 데이터를 나누는지 |
| N7 | 데이터 출처: 화면의 핵심 값(예: 실시간 현황)과 배경 데이터(예: 장소 목록)를 나눠 각각 정한다. 핵심 값을 누가 공급하는가(사용자 제보 / 운영자·제휴처 입력 / 외부 시스템 연동)와 공급자가 올릴 동기 | 사용자 제보에 기대는 서비스면 영향은 `막힘`이다. 제보의 유효 시간과 허위 제보 처리도 함께 정하고 묶음 문항에 넣지 않는다. 배경 데이터를 보여주는 방식(목록 / 지도)과 초기 데이터가 없을 때 첫 화면도 정한다 |
| N8 | 배포·도메인·환경 분리(dev/prod) | 이미 쓰는 스택(Next.js + Vercel, Expo + EAS 등)을 우선한다 |
| N9 | SEO(검색 유입이 필요한가): 메타, OG, 사이트맵, 다국어 hreflang, 지역·카테고리 랜딩 페이지 | 웹 우선이고 장소·지역·상품을 검색해 찾는 서비스면 주 유입 경로이므로 `중요` 이상으로 두고 기본값 묶음에 넣지 않는다. 앱 전용이면 해당 없음 |
| N10 | 분석 이벤트와 에러 모니터링 | 핵심 흐름 이벤트 3~5개면 시작하기에 충분하다 |
| N11 | 캐싱·성능 목표 | 처음엔 정적 생성·CDN 기본값, 측정 후 조정 |
| N12 | 법적 문서: 이용약관, 개인정보 처리방침, 위치·사진 권한 문구 | 수집하는 개인정보 목록부터 정한다 |
| N13 | 운영: 신고·차단(사용자 글이 있으면), 관리자 화면 필요 여부 | 처음엔 DB 대시보드로 대신할 수 있는가 |
