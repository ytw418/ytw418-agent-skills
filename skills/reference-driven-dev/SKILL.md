# 다른 서비스 참고해서 개발하기

저장소 규칙(AGENTS.md·CLAUDE.md)이 먼저다. 브리디면 DB 안전·앱·웹 동시 개발(Parity)·화면 용어·스크린샷·비용 규칙을 그대로 따른다. 이 스킬은 순서와 산출물만 정한다.

## 원칙
- **베끼지 않고 옮긴다.** 참고하는 것은 동작·흐름·정보 구조다. 남의 문구·이미지·아이콘·로고·색 조합을 그대로 가져오지 않는다. 우리 디자인 시스템·용어로 다시 만든다.
- **공개 정보와 실사용만.** 공개 화면·스토어 페이지·공식 도움말·직접 써 본 화면. 로그인 우회·비공개 API 분석·약관 위반 수집은 하지 않는다.
- **문서가 다음 단계의 입력이다.** 각 단계는 앞 단계 문서만 읽고 일할 수 있게 쓴다. 대화 기억에 기대지 않는다.
- **검증은 만든 사람이 아닌 눈으로.** 7단계는 구현한 컨텍스트를 물려받지 않은 서브에이전트가 4단계 문서의 수용 기준만 보고 판정한다.

## 산출물 폴더
`<저장소>/docs/reference/<YYYY-MM-DD>-<참고서비스>-<주제>/` (브리디는 앱 저장소 `docs/reference/`, 웹만 바꾸면 웹 저장소). 캡처는 저장소 밖 `~/bredy-media/<프로젝트>/<날짜-작업>/`에 두고 문서에는 경로나 pr-assets URL 만 적는다(무거운 파일 커밋 금지).

| 파일 | 단계 |
|---|---|
| `1-reference.md` | 다른 서비스 분석 |
| `2-ours.md` | 내 서비스 분석 |
| `3-diff.md` | 기능 차이 |
| `4-apply-plan.md` | 적용 설계(수용 기준 포함) |
| `5-prompt.md` | 구현 프롬프트 |
| `7-verify-<n>.md` | 검증 결과(회차마다) |

각 파일 틀은 `references/templates.md`.

## 1. 다른 서비스 분석 → `1-reference.md`
- 사용자가 말한 기능·화면만 본다(서비스 전체를 훑지 않는다).
- 웹이면 Playwright(모바일 뷰포트 390×844)로 열어 단계마다 캡처한다. 앱이면 스토어 스크린샷·공식 도움말·에뮬레이터 실사용. 로그인이 필요한 화면은 자동화 크롬 프로필을 쓰고, 못 보는 부분은 "못 봄"으로 적는다(추측으로 채우지 않는다).
- 적을 것: 진입 위치, 화면 순서, 각 화면의 요소와 상태(빈·로딩·오류), 사용자 동작과 결과, 숫자(개수·간격·시간·글자 크기 등 눈에 보이는 값), 왜 이렇게 했을지 한 줄 추정(추정이라고 표시).
- 넓은 웹 조사는 서브에이전트(sonnet)에 맡기고 결론만 받는다.

## 2. 내 서비스 분석 → `2-ours.md`
- 같은 기능·화면이 우리 쪽에 어떻게 돼 있는지 **코드와 실제 화면 둘 다** 본다. 파일 경로·컴포넌트·API·DB 열, 지금 화면 캡처.
- 위치를 모르면 graphify 또는 Explore(haiku)로 찾는다. 브리디는 앱·웹 양쪽을 다 적는다.
- 우리만 가진 제약(용어 규칙, 캐시 정책, 광고 자리, 생물 거래 정책 등)도 적는다.

## 3. 기능 차이 정리 → `3-diff.md`
표 한 장: `항목 | 다른 서비스 | 우리 | 차이 종류(없음·다름·더 나음) | 옮길까(예·아니오·보류) | 이유`.
- "옮길까"는 사용자가 요청한 목적에 맞는지로 정한다. 요청 밖이면 보류로 남기고 손대지 않는다.
- 우리가 이미 더 나은 것은 지키는 항목으로 표시한다(바꾸다 망가뜨리지 않게).

## 4. 적용 설계 → `4-apply-plan.md`
"옮길까=예" 항목마다 정확히 무엇을 어떻게 바꿀지 쓴다.
- 바꿀 파일·컴포넌트·API·마이그레이션(있으면 추가형만), 앱·웹 각각.
- 우리 식으로 바꾼 점: 문구(우리 용어), 색·간격(우리 토큰), 다른 서비스와 일부러 다르게 하는 것과 이유.
- **수용 기준**: 예/아니오로 판정할 수 있는 문장, 항목마다 1~3개. 확인 방법(어느 화면에서 무엇을 누르면 무엇이 보인다, 어떤 테스트)까지.
  - 나쁜 예: "지도 시트가 자연스럽다" / 좋은 예: "지도 시트를 손가락으로 끌면 손을 뗄 때까지 시트 위쪽 끝이 손가락 위치를 따라간다(390×844, 앱·웹)".
- 하지 않을 것(비목표)도 적는다.
- 구현이 여러 파일·모듈에 걸치면 이 단계 설계만 Fable 서브에이전트에 맡길 수 있다(전역 CLAUDE.md §8). 넘길 것은 1~3 문서 경로.

설계가 사용자의 판단이 필요한 갈림길(유료화·정책·큰 화면 구조 변경)을 만나면 여기서 한 번 묻고, 나머지는 묻지 않고 진행한다.

## 5. 구현 프롬프트 → `5-prompt.md`
4번을 토대로 구현하는 쪽이 이 파일 하나만 읽고 일할 수 있게 쓴다. 틀은 `references/templates.md` §5.
- 목표 한 문단, 읽을 문서(1~4 경로), 바꿀 파일 목록, 수용 기준 그대로 복사, 지킬 규칙(저장소 규칙 핵심 몇 줄), 하지 말 것, 끝났을 때 남길 것(변경 파일·실행한 검사·캡처 경로).
- 다른 서비스 이름·문구를 코드·화면 문구에 넣지 말라고 적는다.

## 6. 변경
- 기본은 메인이 `5-prompt.md` 를 따라 직접 구현한다. 앱·웹처럼 서로 파일이 겹치지 않는 묶음이 둘 이상이면 각각 서브에이전트(sonnet, worktree 격리)에 `5-prompt.md` 경로와 맡을 범위를 넘겨 병렬로 한다.
- 저장소 규칙대로 검사(브리디 웹 `npm run verify:ci`, 앱 `npx tsc --noEmit`·관련 테스트)를 돌린다. 테스트는 분기 있는 로직에만 최소로 더한다.

## 7. 검증 → `7-verify-<n>.md`
- 새 서브에이전트(sonnet, 구현 컨텍스트 없이)를 부른다. 넘기는 것: `4-apply-plan.md`, `1-reference.md`(비교용), 변경 diff 범위(브랜치·커밋), 로컬 서버/에뮬레이터 띄우는 법. 프롬프트 틀은 `references/templates.md` §7.
- 검증자는 수용 기준마다 **실제로 화면을 띄워 캡처하거나 테스트를 돌려** 통과/실패/확인 못 함을 판정하고, 실패면 무엇이 어떻게 다른지(기대 vs 실제, 캡처 경로)를 적는다. 코드만 읽고 통과시키지 않는다.
- 추가로 본다: 3번에서 "지키는 항목"이 망가지지 않았는지, 다른 서비스 문구·이미지가 그대로 들어오지 않았는지, 저장소 규칙(용어·Parity·캐시) 위반.
- 메인은 결과를 다시 처음부터 검증하지 않는다. 판정이 애매한 항목 하나만 직접 확인한다.

## 8. 재작업(rework)
- 실패 항목이 있으면 `7-verify-<n>.md` 의 실패 항목만 묶어 6단계를 다시 한다(통과한 것은 건드리지 않는다). 그 뒤 7단계를 새 검증자로 다시 돌린다.
- **최대 3회.** 3회째도 실패하면 멈추고 실패 항목·시도한 것·추정 원인·사용자가 정할 것(기준을 바꿀지, 범위에서 뺄지)을 보고한다.
- 같은 항목이 같은 이유로 두 번 실패하면 구현이 아니라 4번 설계가 틀렸을 수 있다. 4번 문서를 고치고(바꾼 이유를 적는다) 5번 프롬프트를 다시 만든 뒤 재작업한다.

## 9. 마무리
- 커밋·PR 은 저장소 규칙대로(브리디: 웹 dev PR + 앱 master, Parity 트레일러, PR 본문 `## 스크린샷` 에 참고 서비스 캡처 | 바뀐 우리 화면).
  - 참고 서비스 캡처는 공개 저장소 pr-assets 에 올리지 않는다(남의 화면). PR 에는 우리 화면만 넣고, 참고 화면은 문서에 설명으로 남긴다.
- 보고: 옮긴 항목·보류한 항목, 검증 회차와 결과, 캡처, 확인 못 한 것.
- 산출물 폴더(1~7 문서)는 커밋한다. 다음에 같은 서비스를 참고할 때 1번을 다시 하지 않고 읽어서 쓴다.
