# 브리디 디자인 자체 심사 (디자인 게이트)

사용자는 매번 화면을 검사하고 싶지 않다. 사용자가 승인한 것보다 더 좋은 디자인이 나오도록, **합격선은 바깥(잘 만든 앱)에서 가져오고, 심사는 사용자 몰래 하고, 사용자에게는 마지막 한 장만 보낸다.** (2026-11-26 사용자 승인)

## 언제 쓰나

| 대상 | 게이트 |
|---|---|
| 새 화면, 화면 개편, 새 시안(목업)·PRD 시안 | **필수** |
| 화면의 큰 덩어리 추가(새 섹션·새 시트·새 카드 줄) | 필수 |
| 문구만, 버그 수정, 색·간격 한두 곳, API·서버만 | 건너뜀 |
| 주 1회 전체 점검 | 9절 '주간 점검 모드' |
| 사용자가 "별로야·구려·찐빠·허접·밋밋해" 라고 함 | 8절 '취향 기록' 먼저 |

## 0. 작업 폴더

`/mnt/project-files/design-gate/<YYYYMMDD>-<화면>/` (맥에서만 돌 때는 `~/Desktop/pro/breeder_web/.design-gate/<…>/`)

```
refs/        기준 앱 캡처 (ref-<앱>-<장면>.png)
ours/        우리 화면 캡처 라운드별 (r1-light.png, r2-light.png …)
pairs/       나란히 붙인 심사용 이미지 (scripts/side_by_side.py)
gate.md      라운드별 판정·고친 것 (사용자에게 보내지 않는 내부 기록)
final.png    사용자에게 보낼 한 장
```

## 1. 먼저 읽는다 (매번)

1. 프로젝트 메모리 `design-taste-log` — 사용자가 "별로"라고 한 기록. **심사 기준에 그대로 들어간다.**
2. 메모리 `design-toss-baseline`, `ux-copy-feedback`, `app-native-feel`
3. 화면에 채택 시안이 있으면 앱 저장소 `docs/design-decisions.md` 해당 행(결정 기록이 기준 앱보다 우선)

## 2. 기준 캡처 (합격선)

같은 기능을 잘하는 앱을 **실제로 캡처**한다. 기억·추측으로 "토스라면 이렇게" 쓰지 않는다.

기본 기준 앱(기능에 맞는 1~2개):

| 우리 기능 | 먼저 볼 앱 |
|---|---|
| 분양 목록·상세·동네·지도·채팅·글쓰기 | 당근 |
| 설정·결제·한 화면 한 목적·입력 흐름·빈 상태 | 토스 |
| 짧은 영상·피드·검색·쇼핑(추천템) | 네이버(클립·쇼핑), 인스타(릴스·피드) |
| 프로필·사진 그리드·스토리·공유 | 인스타 |

**요청 시 참고(기본 아님):** 사용자가 "피들·별꾹도 참고해"라고 하면 넣는다.
- 피들 feedle.me — 파충류·소동물 분양·경매 플랫폼(경쟁사). 분양·경매 화면 비교용
- 별꾹 starkkuk.com (구 꼬리별 kkoristar.com) — 3D 반려동물 추모관(경쟁사). 무지개 마을·추모관 비교용
- 경쟁사는 '이기는지' 보는 대상이지 따라 할 원본이 아니다. 그림·이름·문구를 가져오지 않는다.

캡처 방법(쉬운 순서):
1. 맥 에뮬레이터에 설치된 앱(`adb exec-out screencap -p`). **에뮬레이터는 한 번에 하나**, 쓰고 끈다. 스왑 20GB 넘으면 띄우지 않는다.
2. 모바일 웹(m.naver.com, 당근 웹, feedle.me 등)을 Playwright 모바일 뷰포트(390×844, deviceScaleFactor 2)로
3. 위가 안 되면 앱스토어·플레이스토어 공식 스크린샷 — 이 경우 gate.md 에 '스토어 이미지'라고 적는다

장면은 우리 화면과 같은 상태로 맞춘다(목록 첫 화면 ↔ 목록 첫 화면, 빈 상태 ↔ 빈 상태). 개인정보가 보이면 가린다.

## 3. 만든다

평소대로 만든다(구현이면 `benchmark-build` 4~6단계, 기획이면 `hjjm-prd`). 만든 뒤 우리 화면을 기준과 같은 크기로 찍는다(웹 로컬 서버 Playwright 모바일, 앱 에뮬레이터, 시안은 HTML 을 Playwright 로). 라이트 기본, 색을 바꿨으면 다크도.

## 4. 블라인드 심사 (만든 쪽과 다른 심사자)

**만든 에이전트가 스스로 채점하지 않는다.** Agent 도구로 새 심사자를 띄운다(이 스킬이 하위 에이전트를 쓰라고 지시한다). 심사자에게는 코드·대화·의도를 주지 않고 **이미지와 아래 프롬프트만** 준다.

- `python3 scripts/side_by_side.py <ref.png> <ours.png> pairs/r1.png --shuffle` 로 붙인다. 좌우는 무작위이고 어느 쪽이 우리인지 `pairs/r1.key` 에만 적힌다(심사자에게 주지 않는다). 앱 이름·로고가 보이면 가린다.
- 심사 프롬프트: [references/judge-prompt.md](references/judge-prompt.md) 를 그대로 쓰고, 맨 아래 `{취향 기록}` 칸에 `design-taste-log` 의 '심사 기준' 줄들을 붙인다.
- 기준 앱이 둘이면 각각 따로 붙여 두 번 판정한다.

**합격:** 모든 쌍에서 우리 쪽이 이기거나 '같은 급'이고, 취향 기록 위반이 0개.

## 5. 고치기 — 최대 3번

1. 불합격이면 심사자가 준 '가장 큰 차이 3개'만 고친다(땜질 말고 원인. 예: "카드가 작다"가 아니라 "한 화면에 목적이 둘"이면 구조를 바꾼다).
2. 다시 찍고 **새 심사자**(이전 판정을 모르는)로 다시 판정한다.
3. 3번째도 지면 멈춘다. 가장 나은 라운드를 내보내고, 보고에 "기준 앱보다 아직 약한 점" 한 줄을 붙인다.

gate.md 에 라운드마다 `r<n> | 판정(이김/같은 급/짐) | 확신 | 고친 것 3개` 한 줄씩 남긴다.

## 6. 사용자에게 보내기

- **마지막 결과 한 장만** 보낸다(라이트, 필요하면 다크 한 장 더). 라운드 과정·점수·심사 의견은 보내지 않는다.
- 첨부 한 줄: "당근 ○○ 화면과 나란히 놓고 3번 다듬은 결과예요" 정도. 묻는 사람이 있으면 gate.md 를 준다.
- PR 이면 `## 스크린샷` 에 final 을 넣는다(저장소 규칙). 기준 앱 캡처는 공개 저장소 `pr-assets` 에 올리지 않는다(남의 앱 화면).

## 7. 다른 스레드가 작업 중인 화면

코드를 고치지 않는다. 심사만 하고 결과(판정·가장 큰 차이 3개·final 대신 기준 비교 이미지)를 그 스레드에 `message_thread` 로 넘긴다.

## 8. 취향 기록 — 사용자는 "별로야" 한마디만

사용자가 화면을 보고 부정적으로 말하면(별로·구려·찐빠·허접·밋밋·촌스러·과해·AI 같아 등):

1. 그 턴에 메모리 `design-taste-log` 에 한 줄 추가한다. 사용자에게 이유를 되묻지 않는다.
   `- YYYY-MM-DD <화면> | 사용자: "<원문>" | 문제(추정): <무엇이 별로였나> | 심사 기준: <다음에 심사자가 확인할 한 문장>`
2. '심사 기준'은 다른 화면에도 통하는 문장으로 쓴다(learn-taste 스킬의 '클래스 수준'). 예: "알록달록 여러 색 장식이 있으면 불합격".
3. 같은 지적이 두 번이면 기존 줄을 더 엄격하게(숫자·금지어로) 고친다. 코드로 잡을 수 있으면(색 hex, 금지 클래스) 린트 후보로 적는다.
4. 사용자가 고른 안·승인한 안("좋아", "이걸로")도 '좋았던 것' 줄로 남긴다 — 무엇이 이겼는지가 다음 합격선이다.

## 9. 주간 점검 모드 (주 1회, 맥 Paseo 일정)

1. 앱 주요 화면을 에뮬레이터로 찍는다(목록은 [references/weekly-screens.md](references/weekly-screens.md)). 에뮬레이터를 이미 다른 작업이 쓰고 있으면 웹 로컬 서버 캡처로 대신한다.
2. 화면마다 2절 기준 앱 한 장과 붙여 4절 심사자에게 판정시킨다(화면 수가 많으니 sonnet 심사자 하나가 여러 쌍을 판정해도 된다, 단 만든 쪽 맥락은 주지 않는다).
3. '짐' 확신이 큰 순서로 **가장 못생긴 3개**를 고른다. 지난주에 고르고 사용자가 거절한 화면은 뺀다(`weekly/rejected.md`).
4. 3개마다 개선 시안 한 장(HTML 목업 → 캡처)을 만든다. **코드는 고치지 않는다.**
5. 결과를 `~/Desktop/pro/breeder_web/.design-gate/weekly/<날짜>/report.md`(지금 화면 | 시안 | 고칠 점 한 줄)로 남기고 Slack(`scripts/slack-notify.sh "이번 주 고칠 화면 3개" "<화면1>, <화면2>, <화면3> — 이거 고칠까요?"`)으로 묻는다.
6. 사용자가 "고쳐"라고 하면 그때 그 화면을 1~6절 순서로 구현한다.
