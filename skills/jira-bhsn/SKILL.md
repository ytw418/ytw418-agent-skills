# BHSN Jira 개발 워크플로우

Jira 티켓 기반으로 브랜치 생성 → 개발 → PR → 리뷰까지의 전체 사이클을 관리한다.

> **Jira 댓글 (2026-10-22 사용자 결정):** 작업 중 공유할 내용(진행 상황, 원인 분석, PR 링크, 확인 요청 등)이 있으면 판단해서 댓글을 단다 (`jira_add_comment`). 단, **사람 멘션이 들어간 댓글은 사용자 승인 후에만** 단다 — 아래 '4-1. Jira 댓글' 참고.

> **Jira 상태 임의 변경 금지 (MANDATORY):** 사용자가 명시적으로 요청했거나 변경할 상태를 사용자에게 사전 확인받은 경우에만 티켓 상태를 전환한다. 작업 시작, PR 생성, 리뷰 준비 완료 등의 이벤트만으로 상태를 자동 변경하지 않는다.

> **QA 상태 전환 금지 (MANDATORY):** Jira 티켓을 `QA`, `QA 요청`, `QA 진행` 등 QA 관련 상태로 변경하지 않는다. PR 생성, 리뷰 완료, 배포 완료 또는 테스트 통과를 QA 상태 전환의 근거로 추론하지 않는다.

## 1. 티켓 식별 (작업 시작 전 필수)

**코드를 작성하기 전에 반드시 Jira 티켓을 식별한다.**

1. **사용자가 티켓 코드를 명시** (e.g. `BA-2031`, `AT-150`):
   - `jira_get_issue`로 summary, description, acceptance criteria, status를 조회.
2. **브랜치명에 티켓 코드 포함** (e.g. `feat/BA-2031-some-feature`):
   - 브랜치명에서 티켓 코드를 추출하여 `jira_get_issue`로 조회.
3. **사용자가 티켓 코드 없이 작업을 설명**:
   - 사용자에게 해당 Jira 티켓을 질의. 티켓 없이 진행하지 않는다.
   - 사용자가 모르면 `jira_search`로 검색.
   - **보드 선택 기준:** (섹션 8의 보드 레퍼런스 참조)
     - 레포 `CLAUDE.md`에 Primary Board가 명시되어 있으면 그것을 우선 참조.
     - **보드가 불분명한 경우**, `jira_search`에 `assignee = currentUser() ORDER BY updated DESC`로 사용자 할당 티켓을 조회하여 프로젝트 키 분포를 분석하고, 결과를 사용자에게 제시하여 확인받는다.
   - 매칭 티켓이 없으면 생성 여부를 사용자에게 확인.
   - **티켓 생성 시** `assignee`를 현재 사용자로 설정 (`jira_get_user_profile`로 확인).
   - **티켓 생성 시** 적절한 상위 이슈(Epic/Story) 검색 후 `parent` 필드로 연결. 적절한 상위 이슈가 없으면 생략.
   - **티켓 생성 규칙은 '1-1. 티켓 생성 규칙'을 따른다.**
4. 컨텍스트가 불분명하면 `jira_search`로 관련 이슈 탐색.

## 1-1. 티켓 생성 규칙 (2026-10-22 사용자 결정)

**이슈 타입 — 크기로 나눈다**
- **스토리**: 큰 작업 단위(여러 파일·화면에 걸친 기능, 하루 넘게 걸리는 일, PR이 따로 나가는 단위). **브랜치는 스토리 티켓으로만 만든다.**
- **작업**: 작은 단위. 스토리 안의 작업 구분·내용 정리를 다른 사람이 보기 편하게 하려는 용도다. **작업 티켓으로는 브랜치를 만들지 않는다.** 커밋·PR 제목도 스토리 티켓 키를 쓴다.
  - 작업 티켓은 관련 스토리와 묶는다(`parent`로 걸 수 있으면 parent, 안 되면 `jira_create_issue_link`로 스토리와 연결).
- 크기가 애매하면 생성 전에 사용자에게 스토리/작업 중 무엇으로 할지 묻는다.

**기획서·피그마로 티켓 만들기 ("이걸로 티켓 만들어줘")**
1. 기획서(Confluence 등)와 Figma를 읽고 FE 범위를 정리한다.
2. **스토리 1개**를 만든다 — 기능 전체 단위. 설명에 기획서·Figma 링크와 범위 요약을 넣는다.
3. 그 아래 **작업 티켓을 최대 5개**로 나눈다. 화면·흐름 단위로 묶어 다른 사람이 진행 상황을 알아보기 쉽게 나누고, 5개를 넘을 것 같으면 묶어서 5개 이하로 맞춘다. 범위가 작으면 작업 티켓 없이 스토리만 만들어도 된다.
4. 만들기 전에 스토리 제목, 작업 티켓 목록(제목·포인트), 와쳐를 표 하나로 보여주고 확인받은 뒤 한 번에 생성한다.

**스토리 포인트 — 항상 넣는다**
- 필드: ALLIBEE는 `customfield_10016`(Story point estimate). 다른 프로젝트는 `jira_search_fields`로 "story point"를 찾아 그 프로젝트 티켓에 실제 값이 들어 있는 필드를 쓴다.
- 기준(피보나치): 1 = 문구·설정 수준, 2 = 반나절, 3 = 하루, 5 = 2~3일, 8 = 일주일 가까이. 8을 넘으면 스토리를 나누자고 제안한다.
- 스토리 포인트는 그 아래 작업 티켓 포인트의 합으로 맞춘다.
- 생성 보고에 넣은 포인트와 근거를 한 줄로 적는다.

**와쳐 — 연관 있는 사람을 넣는다**
- 티켓 내용·상위 이슈·관련 Slack/Confluence/PR에서 연관된 기획자·BE·디자이너·QA를 찾아 `jira_add_watcher`로 추가한다. 사용자 본인(담당자)은 기본으로 들어간다.
- 사람은 `jira_search_assignable_users`로 accountId를 확인하고, 동명이인이거나 누가 연관인지 불확실하면 사용자에게 묻는다.
- 와쳐 추가는 승인 없이 하되, 생성 보고에 누구를 넣었는지 적는다. (멘션 댓글은 별개 — 4-1의 승인 규칙을 따른다.)

## 2. 스프린트 컨텍스트 조회

1. `jira_get_agile_boards`로 관련 보드(BA 또는 AT) 조회.
2. `jira_get_sprints_from_board` (state="active")로 현재 스프린트 조회.
3. `jira_get_sprint_issues`로 스프린트 이슈 목록 조회.
4. Confluence에서 스프린트 계획 문서 검색.
5. 스프린트 컨텍스트를 찾을 수 없으면 사용자에게 질의.
6. Jira 티켓과 스프린트 계획을 교차 확인.

## 3. 브랜치 생성

- **브랜치는 스토리 티켓으로만 만든다.** 사용자가 작업 티켓 키를 주면 상위/연결된 스토리를 찾아 그 키로 브랜치를 만든다(스토리를 못 찾으면 사용자에게 묻는다).
- 브랜치 이름은 레포 규칙을 우선한다 (예: allibee-frontend-react는 `feature/<스토리키>`).

1. 해당 티켓의 feature branch가 이미 있으면 checkout.
2. 없으면 **`develop`** 에서 생성:
   ```bash
   git fetch origin
   git checkout -b feat/BA-XXXX-short-description origin/develop
   ```
3. `main`/`master`에서 브랜치하지 않는다 — 항상 `develop` 기반.
4. `develop`에서 직접 코딩하지 않는다 — 항상 feature branch 사용.

## 4. 작업 중

- 티켓 상태 변경이 필요해 보여도 먼저 현재 상태와 변경하려는 상태를 사용자에게 알리고 확인받는다.
- 사용자가 명시적으로 상태 변경을 요청한 경우에만 `jira_get_transitions` + `jira_transition_issue`를 사용한다 (e.g. "To Do" → "In Progress").
- QA 관련 상태로의 전환은 제안하거나 실행하지 않는다.
- 공유할 내용이 있으면 Jira 댓글을 단다 (4-1).

### 4-1. Jira 댓글

- **멘션 없는 댓글**: 승인 없이 단다. 단 뒤 사용자에게 티켓 키와 댓글 요지를 한 줄로 알린다.
  - 쓸 만한 때: 원인 분석 결과, 구현 방향 결정, PR 링크, 배포 반영, BE·디자인 확인이 필요한 지점 정리.
  - 같은 내용을 반복해 달지 않는다. 짧고 사실 위주로, Claude가 썼다는 표시는 남기지 않는다.
- **멘션(@담당자)이 들어간 댓글**: 달기 전에 반드시 사용자 승인을 받는다.
  1. 멘션할 사람을 `jira_search_assignable_users`(또는 `lookupJiraAccountId`)로 찾아 이름·이메일·accountId를 확인한다. 동명이인이면 사용자에게 고르게 한다.
  2. 대상자와 댓글 본문 전체를 `AskUserQuestion` 승인 카드로 보여준다 (보내기 / 멘션 빼고 보내기 / 보내지 않기).
  3. 승인되면 본문에 `[~accountid:<accountId>]` 형식으로 멘션을 넣어 단다.
  - 사용자가 "○○님 태그해서 달아줘"처럼 대상과 내용을 직접 지시한 경우도 본문 확인을 한 번 받는다.
- **멘션 댓글 쓰는 법**: 받는 사람이 티켓을 다시 뒤지지 않아도 알 수 있게 쓴다.
  - 꼭 들어갈 것: **어느 화면의 어느 부분**인지(화면 경로·영역 이름), **어떤 상황에서** 생기는지(계정·데이터 조건, 재현 순서), **무엇을 해 달라는지**(확인·결정·수정 중 하나).
  - 짧게: 3~5줄. 인사·서론·요약 반복·"~드립니다" 연발·불릿 남발·이모지 없이 동료에게 메신저로 묻듯 쓴다. 근거 링크(PR, 스크린샷, API 경로)는 한 줄로 붙인다.
  - 예:
    ```
    @이태희 계약 검토 > 상세 검토 탭 상단 안내 문구 확인 부탁드려요.
    검토 생략된 계약서(dev ws 1234, 문서 5678)로 들어가면 사유 필드가 null로 와서 안내가 안 뜹니다.
    GET /contracts/{id}/review 응답에 skip_reason 내려주실 수 있을까요?
    ```
    ```
    @노홍석 Cue 모바일 바텀시트 닫힘 동작 하나 정해주세요.
    답변 생성 중에 시트를 아래로 끌어 닫으면 생성이 계속 도는데, 다시 열면 중간부터 보입니다.
    닫을 때 생성을 멈출지, 그대로 둘지 알려주시면 맞춰 넣을게요. 녹화: <링크>
    ```
    ```
    @디자이너 워크스페이스 상세 > 사용 가능 크레딧 카드, 타입이 4개 이상일 때 디자인이 없어요.
    엔터프라이즈 워크스페이스는 타입이 5개라 카드가 두 줄로 넘칩니다. 스크린샷: <링크>
    스크롤로 둘지 접기로 둘지 피그마에 하나 추가 부탁드려요.
    ```
- 이미 단 댓글 수정은 `jira_edit_comment`를 쓴다 (멘션을 새로 추가하는 수정이면 승인 필요).

## 5. PR 워크플로우

1. **첫 커밋 push 후** 즉시 **draft PR** 생성 (타겟: `develop`):
   ```bash
   gh pr create --base develop --draft --assignee ytw418 --title "BA-XXXX Short description" --body "..."
   ```
   - PR 제목의 Jira 티켓 코드는 대괄호로 감싸지 않는다. 올바른 형식은 `BA-XXXX Short description`이다.
   - **Assignee는 항상 `ytw418`로 등록한다.** 누락된 경우 `gh pr edit <pr-number> --add-assignee ytw418`로 보정한다.
2. 추가 커밋은 같은 브랜치에 push — draft PR이 자동 업데이트.
3. **작업 완료 후** (테스트/스타일 통과) ready for review로 전환:
   ```bash
   gh pr ready
   ```
4. PR 오픈 후에도 Jira 티켓을 자동으로 "In Review"로 전환하지 않는다. 사용자가 요청하거나 사전 확인한 경우에만 전환한다. PR 링크는 필요하면 멘션 없는 댓글로 남길 수 있다.

**단일 커밋 변경이라도 draft → ready 단계를 생략하지 않는다.**

## 6. 완료 후

- 티켓 상태 전환이 필요하면 목표 상태(e.g. "In Review" 또는 "Done")를 사용자에게 명시하고 확인받은 뒤 전환한다.
- 작업 내용 요약은 사용자에게 전달하고, 티켓에 남길 가치가 있으면 멘션 없는 댓글로도 남긴다.

## 7. 문서화 (선택)

PR 오픈 + Jira 업데이트 완료 후 사용자에게 문서화 여부를 질의.

**Confluence 문서 작성 시:**

문서화 대상:
- API 인터페이스 변경, 새 기능, 작업 상태, 주요 결정 사항, 마이그레이션 안내

포맷 규칙:
- 제목/본문 **한국어** 작성 — e.g. `BA-2031 파일 파싱 실패 시 INTERRUPT 필드 추가`
- `jira_create_remote_issue_link`로 Confluence 문서를 Jira 티켓에 연결.
- 기존 스프린트/기능 페이지가 있으면 중복 생성 대신 업데이트.

**Content size limitation (CRITICAL):**

Atlassian MCP (`create_confluence_page`, `update_confluence_page`)는 ~3,000~5,000자 이상의 페이로드에서 무한 대기한다.

- 단일 호출은 ~3,000자 이하로 유지.
- 대형 문서는 부모 페이지(요약+목차) + 자식 페이지(`parentId` 사용)로 분할.
- 크기 초과 실패 시 동일 페이로드 재시도 금지 — 줄인 후 재시도.

## 8. 레포별 Jira 보드 설정

- 이 영역의 내용은 `bhsn-claude-code` repo 내부에서는 고려하지 않습니다.
- 레포 루트 `CLAUDE.md`에 Primary Board가 명시되어 있으면 그것을 우선 참조.
- **Primary Board가 불분명한 경우**, 아래 순서로 보드를 확인한다:
  1. `jira_get_user_profile`로 현재 사용자 계정을 확인한다.
  2. `jira_search`에 `assignee = currentUser() ORDER BY updated DESC` 쿼리를 사용하여 사용자에게 할당된 최근 티켓 목록을 조회한다.
  3. 조회된 티켓들의 프로젝트 키(BA, AT 등) 분포를 분석하여 주로 사용하는 보드를 파악한다.
  4. 분석 결과를 사용자에게 제시하고, 아래 보드 레퍼런스를 참고하여 올바른 보드를 확인받는다:
     - e.g. "최근 할당된 티켓 10건 중 BA 7건, AT 3건입니다. 이 레포의 Primary Board를 BA로 설정할까요?"
  5. 사용자 확인 후 레포 `CLAUDE.md`에 기록:
