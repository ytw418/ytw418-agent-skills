# Vercel 비용 다이어트

작은 서비스(하루 방문자 수백 명)가 Vercel Pro 에서 한 달 $100 넘게 낸 뒤 하루 $1 밑으로 내린 방법을 정리했다. 순서는 **청구 내역 측정 → 전체 표 → 비용 기준으로 결정 → 고치기 → 다시 측정**이다. 측정하기 전에는 아무것도 고치지 않는다.

핵심은 하나다. **방문자가 적은 서비스는 캐시 시간이 짧으면 거의 매번 MISS 다.** 항목 하나하나 땜질하지 말고, 페이지·API 전체를 놓고 "누구에게나 같은 응답인가, 몇 쪽인가, 얼마나 자주 바뀌나"로 정한다.

## 1. 측정 — 어디서 돈이 나가는지부터

- 청구 내역을 **프로젝트별·항목별·하루 단위**로 본다. CLI: `vercel api /v1/billing/charges` (FOCUS 형식, 하루 단위). 대시보드 Usage 화면도 된다.
- 하루 경계는 미국 기준이라 한국 시간과 어긋난다. 그리고 청구 자료는 하루쯤 늦게 들어온다. "오늘 얼마"는 아직 모른다고 답한다.
- Pro 요금제의 월 $20 은 **사용량 크레딧으로 돌려준다.** 하루 약 $0.65 의 기본료 줄은 사용량이 아니니 프로젝트 비용에서 뺀다. 지출 한도도 이 기본료를 뺀 사용량으로 계산된다.
- 같은 팀에 프로젝트가 여럿이면 반드시 나눠 본다. "거의 다 A 프로젝트"라고 추측했다가 실제로는 B 가 두 배였던 적이 있다.
- 배포 기록(`vercel ls`), 요청 수(`vercel metrics vercel.request.count --group-by <차원>`), 방화벽 요약(`vercel firewall traffic list`)으로 원인을 찾는다. 차원을 여러 개 묶는 조회는 유료(Observability Plus)라 하나씩 본다.

자주 나오는 원인과 항목:

| 청구 항목 | 흔한 원인 |
|---|---|
| 빌드 CPU | 작업 브랜치·PR 마다 프리뷰 빌드, 커밋마다 재빌드, 잦은 운영 배포 |
| ISR 쓰기 | 짧은 `revalidate`, 쪽 수 많은 상세에 ISR, 배포 뒤 미리 채우기(warm), 매일 전체 갱신 |
| 함수 실행 | 캐시 없는 공개 API, 짧은 폴링, 서버가 자기 API 를 HTTP 로 다시 호출, 링크 프리패치 |
| 전송량(Origin) | 위 둘의 결과, 큰 HTML·RSC, 캐시 안 되는 이미지·아이콘 |
| 요청 수 | 수집기·나쁜 봇, 화면에 보이기만 해도 미리 받는 링크 |

## 2. 전체 표 — 고치기 전에 먼저 보여 준다

페이지와 API 를 전부 한 표에 적고, 사용자에게 보여 준 뒤 고친다.

| 칸 | 적을 것 |
|---|---|
| 대상 | 경로 |
| 성격 | 공개(누구나 같음) / 검색 유입 / 로그인 개인 |
| 쪽 수 | 대략(상세는 글 수만큼) |
| 바뀌는 빈도 | 글이 고쳐질 때만 / 분 단위 / 계속 |
| 하루 요청 | 측정값 |
| 지금 | 렌더링·캐시·폴링 |
| 바꿀 것 | 아래 3장 기준 |

## 3. 비용 기준으로 정하기

### 3-1. 빌드
- **Vercel 은 main(운영)만 빌드한다.** 프로젝트 설정 Ignored Build Step 과 `vercel.json` `git.deploymentEnabled` 로 작업 브랜치(특히 AI 에이전트 브랜치)는 끈다. 에이전트가 커밋마다 푸시하면 하루 수백 번 빌드된다.
- 빌드에서 타입 검사를 빼고(`typescript.ignoreBuildErrors`), 대신 머지 전에 로컬·CI 에서 typecheck 를 꼭 돌린다.
- 더 줄이려면 **로컬에서 빌드해서 올린다**: `vercel pull --environment=production` → `vercel build --prod` → `vercel deploy --prebuilt --prod --skip-domain` → 배포 주소에서 주요 API·이미지·OG 가 200 인지 확인 → `vercel promote`. Apple Silicon 맥에서 만든 함수는 linux-arm64 라 Prisma 를 쓰면 `binaryTargets` 에 `linux-arm64-openssl-3.0.x` 가 있어야 한다(없으면 DB API 가 전부 500).
- 프리뷰가 없어지니 화면 확인은 로컬 서버를 Playwright 모바일 뷰포트로 찍어서 한다. 마이그레이션은 운영 전에 dev DB 에 `migrate deploy` 로 먼저 돌린다.
- **운영 배포는 묶는다.** 배포마다 ISR·CDN 캐시가 새로 시작돼 다시 채우는 비용이 든다.

### 3-2. ISR 이냐, 요청마다 그리고 CDN 에 두느냐
ISR 저장 한 번이 렌더 한 번보다 훨씬 비싸다. 실측 예: 상세 한 장 HTML+RSC 약 165KB → ISR 쓰기 약 21단위(8KB 당 1단위) ≈ $0.00009, 함수 렌더 1회 ≈ $0.00001. **저장 1번 = 렌더 9~20번**이다. 배포마다 ISR 이 비워지니, 쪽 수가 많고 장당 조회가 적은 롱테일 상세는 "한두 번 보이고 비워짐"이라 ISR 이 손해다. (가격표는 바뀌니 vercel.com/pricing 에서 다시 계산한다.)

- **ISR**: 쪽 수가 적고 많이 열리는 화면만(홈, 목록 첫 화면, 랭킹, 가이드). 주기는 분~시간 단위, 그리고 글을 쓰면 그때 갱신.
- **상세(롱테일)**: `revalidate`·`generateStaticParams` 를 두지 않는다(동적 경로 기본값이 요청마다 렌더다. `force-dynamic` 도 필요 없다). 대신 HTML 을 CDN 에 둔다(3-3).
- 배포 뒤 전체 미리 채우기, 매일 전체 다시 그리기는 하지 않는다. 최근 글만 채우고 나머지는 처음 열릴 때 만들어지게 둔다.

### 3-3. 상세 HTML 과 공개 API 는 같은 태그로 CDN 캐시
1. **사람마다 다른 값은 HTML 에 넣지 않는다.** 좋아요 수·찜·조회수·댓글, 내 좋아요 여부·수정 버튼·채팅 버튼·권한은 화면이 API 로 따로 받는다(CSR). 캐시되는 페이지의 서버 렌더는 쿠키·헤더를 읽지 않는다(`next/headers` 금지). 이걸 깨면 **다른 사람 화면이 CDN 으로 샌다.** 깨면 실패하는 테스트를 하나 둔다.
2. **HTML 과 비로그인 API 를 같은 태그로 캐시한다.** 태그 이름은 한 곳에서 만든다(`product-12`, `post-5`, `user-3`). 페이지는 `addCacheTag`, API 는 `Vercel-Cache-Tag` 헤더. 둘 다 `@vercel/functions` 공식 함수를 쓴다.
3. **만료는 안전망으로 하루**(`s-maxage=86400`). 비우기를 놓쳐도 낡은 화면이 영원히 남지 않게 하는 용도다. 입찰처럼 비우지 않는 쓰기로 계속 바뀌는 화면과 비우는 태그가 없는 화면은 5분.
4. **글 내용이 바뀔 때만 비운다**: 제목·가격·본문·상태(예: 판매중→완료)·숨김·삭제, 작성자 닉네임·사진. 쓰기 API 를 공용 래퍼 하나로 지나게 하고 거기서 `invalidateByTag`. **좋아요·찜·조회·댓글·입찰·투표로는 비우지 않는다.** 비우면 캐시가 사실상 없어진다.
5. Next 는 동적 페이지에 `Cache-Control: no-store` 를 붙인다. Vercel CDN 은 `Vercel-CDN-Cache-Control` 을 먼저 따르니 `next.config.js` `headers()` 에서 그 헤더를 준다. 화면 이동용 RSC 요청은 `missing: [{ type: "header", key: "rsc" }]` 로 빼서 HTML 만 캐시한다.
6. **로그인 토큰이 붙은 응답은 캐시하지 않는다**(`private`). Vercel CDN 은 `Authorization` 이 붙은 요청을 캐시하지 않는다. 그래서 누구에게나 같은 데이터(홈 피드·배너·공지·카테고리·목록)는 앱·웹 모두 **토큰 없이** 부른다. 차단 같은 개인 거르기는 화면에서 한다. 모바일 앱이 모든 요청에 토큰을 붙이면 CDN 캐시를 늘려도 앱 사용자에게는 효과가 0 이다.
7. 공개 목록은 분 단위로 길게(5~30분), 쓰기 때 태그로 비운다. 캐시 시간은 상수 파일 한 곳에 모은다.

### 3-4. 함수가 두 번 도는 곳 없애기
- 서버 컴포넌트가 자기 API 를 `fetch("https://내도메인/api/...")` 로 부르지 않는다. 같은 프로세스에서 핸들러 함수를 바로 부른다. 이때 핸들러가 단 캐시 태그는 HTML 응답에 닿지 않으니 페이지에서 따로 단다.
- 숫자 주소 → 제목 주소 리다이렉트처럼 결과가 안 바뀌는 조회는 하루 캐시.

### 3-5. 폴링
- 화면이 보일 때만 돈다(웹 SWR·탭 숨김, 앱 백그라운드). 끝난 것(마감된 경매)은 멈춘다.
- 간격 기준 예: 안 읽은 알림·채팅 수 60초, 채팅 목록 15초, 열린 채팅방 5초, 진행 중 경매 5초(끝나면 멈춤).
- 여러 사람이 보는 같은 데이터를 짧게 폴링하면 비로그인 응답을 몇 초라도 CDN 에 둬서 묶는다.

### 3-6. 링크 프리패치
- Next `<Link>` 기본값은 **화면에 보이기만 해도** 미리 받는다. 모바일에서 피드를 내리면 카드마다 요청이 나간다.
- 공용 링크 컴포넌트를 하나 만들어 "마우스를 올리거나 손가락이 닿을 때만" 받게 하고, 하단 탭처럼 자주 가는 몇 곳만 기본값으로 둔다. 옛 `<Link>` 직접 사용은 lint 로 막는다.

### 3-7. 정적 파일
- `public/` 아이콘·그림은 기본 `max-age=0` 이라 화면마다 다시 확인한다. 이름이 그대로인 채 바뀔 수 있으면 브라우저 1일 · CDN 30일. `sw.js`·`ads.txt` 처럼 바로 바뀌어야 하는 파일은 뺀다.

### 3-8. 봇·수집기
- 요청이 갑자기 늘면 비용 코드보다 먼저 방화벽 요약에서 IP·UA·ASN·나라를 본다. 한 IP 가 사이트 전체를 훑는 경우가 흔하다.
- UA 정규식 차단 규칙(SEO 크롤러·AI 수집기 중 필요 없는 것)과, 근거가 있을 때만 나라 차단을 건다.
- **우리 것은 막지 않는다**: 앱 HTTP 클라이언트(`okhttp`, `CFNetwork`), 서버 내부 호출(`node`), 캡처 자동화, 업타임 모니터, 링크 미리보기 봇. 관리형 봇 차단은 앱 API 를 막을 수 있어 켜기 전에 앱 요청으로 시험한다.

### 3-9. 크론·동기화
- 외부 데이터 동기화에는 하루 처리 상한(예: 5,000건)과 정리 주기(예: 30일)를 둔다. 결과를 남겨 실패를 바로 볼 수 있게 한다.

## 4. 고치기 규칙
- 새 페이지·API 는 처음부터 이 기준으로 만든다. 사용자에게 묻지 않는다.
- PR 본문에 `## 캐시·폴링` 을 넣는다: 공개/개인, 쪽 수, 바뀌는 빈도, 렌더링(ISR 주기·고칠 때만·CSR), 캐시 시간·태그·비우는 쓰기, 폴링 간격.
- 규칙은 저장소 `AGENTS.md`(또는 `CLAUDE.md`)에 적고, 어기면 실패하는 테스트나 훅으로 강제한다. 문서만 두면 다음 에이전트가 또 짧은 ISR 을 만든다.

## 5. 다시 측정 — "줄었다"는 숫자로만 말한다
- 운영 배포 직후: `curl -sI <주소>` 를 두 번 보내 두 번째가 `x-vercel-cache: HIT` 인지, 글을 고친 뒤 다음 요청이 새 내용인지 본다. `invalidateByTag` 는 옛 응답을 한 번 더 주고 뒤에서 갱신하므로 첫 요청이 옛 내용일 수 있다.
- 비용은 **배포가 없던 온전한 하루**끼리 비교한다. 배포한 날은 캐시가 비워져 있어 비교가 안 된다.
- 효과가 안 보인 변경은 "효과 있음"이라고 쓰지 않는다. 예: 빌드에서 타입 검사 빼기는 거의 효과가 없었고, 작업 브랜치 빌드 끄기는 컸다.
- 지출 한도(Spend Management)는 걸어 두되, 한도에 닿으면 프로젝트가 멈추는지 알림만 오는지 확인하고 사용자에게 알린다.

## 하지 말 것
- 측정 없이 "아마 이게 원인"이라고 고치기.
- 좋아요·조회수 쓰기에서 상세 캐시 비우기.
- 로그인 응답을 `public` 으로 캐시하기, 캐시되는 서버 렌더에서 쿠키 읽기.
- 사용자가 모르는 새 서비스·인프라(새 CDN, 새 DB, 앞단 워커)를 마음대로 추가하기. 가장 기본 구조로 먼저 줄이고, 추가는 사용자가 정한다.
